# M5 — 데이터 갱신 자동화

커밋: `M5: 게임 데이터 월간 갱신 자동화`

M5 중 **데이터 갱신 자동화만** 먼저 했습니다. 나머지(EN 전환 완성, 인격 아이콘)는 UI 재설계 뒤로 미룹니다 — 지금 만들면 새 디자인에서 다시 만들게 됩니다.

## 무엇을 했나

`npm run data:update`를 매월 1일에 자동으로 돌려, 원본 게임 데이터가 바뀌었으면 드래프트 PR을 열어 둡니다. 사람은 "변경 요약을 읽고 머지할지 정하는" 일만 하면 됩니다.

| 파일 | 역할 |
|---|---|
| `.github/workflows/data-update.yml` | 매월 1일 18:00 UTC + 수동 실행. fetch → build → 변경 감지 → diff 요약 → changelog → `npm run check` → 브랜치 푸시 → 드래프트 PR |
| `scripts/changelog-entry.ts` | `npm run data:changelog`. 이전 커밋의 `meta.json`과 비교해 `docs/research/changelog.md`에 한 줄 추가 |
| `scripts/lib/changelog.ts` + 테스트 10개 | 그 한 줄을 만드는 순수 함수(카운트 증감, sha 이동, 중복 방지) |

## 읽는 순서

1. `.github/workflows/data-update.yml` — 특히 주석으로 적어 둔 판단 근거 4가지
2. `scripts/lib/changelog.ts` → `scripts/lib/changelog.test.ts`
3. `scripts/changelog-entry.ts`
4. `.claude/skills/update-game-data/SKILL.md` 6절 — 런북과 자동화가 같은 절차를 가리키는지

## 설계 판단

**원본 파일을 못 받으면 빌드하지 않고 멈춘다.** `fetch-sources`는 404를 치명적으로 보지 않고 계속 진행합니다(시즌 교체 시 파일 이름이 바뀌는 게 정상이라서). 하지만 자동 갱신에서는 반쯤 받아온 데이터로 빌드하면 "기프트 200개 삭제" 같은 가짜 PR이 열립니다. 그래서 fetch가 실패하면 요약에 원인을 적고 거기서 끝냅니다.

**브랜치 이름에 `dataVersion`을 넣어 force push를 없앴다.** `dataVersion`은 입력 전체의 해시라, 내용이 다르면 브랜치 이름이 다릅니다. 같은 데이터로 다시 돌리면 같은 브랜치에 같은 커밋이라 푸시가 no-op이고, 사람이 그 PR 브랜치에 올린 수정 커밋을 덮어쓸 일이 없습니다.

**검사를 워크플로 안에서 돌린다.** `GITHUB_TOKEN`이 연 PR에는 다른 워크플로가 붙지 않는 게 GitHub 사양이라 `ci.yml`이 실행되지 않습니다. 그래서 `npm run check`를 잡 안에서 돌리고 결과를 PR 본문에 적습니다. **실패해도 PR은 엽니다** — 조건 파서 스냅샷이 깨지는 건 "게임이 바뀌었다"는 신호일 수 있어 사람이 diff를 봐야 하기 때문입니다. 대신 잡은 빨갛게 끝나 알림이 갑니다.

**변경 감지는 `git status`로 한다.** `git diff`는 추적 중인 파일만 봅니다. 시즌이 바뀌면 `data/raw`에 새 파일이 생기는데 그건 untracked라 diff에 안 잡혀서, 새 팩이 통째로 들어온 갱신을 "변경 없음"으로 흘려보내게 됩니다.

**changelog는 커밋 전에 쓴다.** 비교 대상이 git에 남아 있는 이전 `meta.json`이라, 커밋 후에 돌리면 비교할 게 없습니다. 같은 내용은 두 번 기록하지 않습니다(날짜 칸을 뺀 나머지가 같으면 건너뜀).

## 검증 로그

```
$ npx vitest run scripts/lib/changelog.test.ts     → 10 passed
$ npm run check                                    → 135 tests passed
$ npm run -s data:changelog                        → "meta.json이 HEAD와 같습니다 — 기록할 변경이 없습니다"

워크플로 명령을 로컬에서 순서대로 재현 (data/curated/notes.json에 가짜 변경을 넣어 시뮬레이션):
  data:build                → dataVersion 7.f85f9464 → 7.4e9fd33f
  git diff --quiet -- data public/data  → changed=true
  data:diff                 → gifts 446 -> 446 (+0 / -0 / ~1), changed: 9088 진혼
  data:changelog            → | 2026-09-11 | 7.4e9fd33f | ... | 수치 변동 없음 (내용만 변경) |
  변경을 되돌린 뒤 data:build → 산출물 원상 복구 확인

YAML 파싱 + 모든 run 블록 `bash -n` → 통과
변경 감지: data/raw에 untracked 파일만 있을 때 changed=true, 아무것도 없을 때 changed=false
```

실제 스케줄 실행은 이 워크플로가 **기본 브랜치에 머지된 뒤**에만 시작됩니다(GitHub는 기본 브랜치의 schedule만 실행). 그 전에 시험하려면 머지 후 Actions 탭에서 **Update game data → Run workflow**.

## 봐 주셨으면 하는 점

1. 주기가 월 1회로 맞나요? 림버스 패치는 보통 격주 목요일이라 `0 18 * * 5`(매주 금요일 03:00 KST) 쪽이 나을 수도 있습니다.
2. `npm run check` 실패 시에도 PR을 여는 선택이 맞나요? (대안: 열지 않고 실패만 알림)
3. 저장소 설정에서 **Settings → Actions → General → Workflow permissions**의 "Allow GitHub Actions to create and approve pull requests"를 켜 주셔야 PR 생성이 됩니다. 꺼져 있으면 브랜치 푸시까지는 되고 PR만 실패합니다.
