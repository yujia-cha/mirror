# M23 — 팩 탐색 재작성(완전 탐색) · 「반드시」 단조성 보장 · 얽힘 잠금 해제와 재료 두 몫

커밋: `M23: 팩 분기 + 매칭 탐색 · 우선순위 단조성 · 얽힘 잠금 해제, 재료 몫을 따로 확보`

## 무엇을 했나

사용자 지시 둘. 「완전 탐색이 무리인지 알려 달라, 더 나은 알고리즘을 시도해 달라」와 「얽힘 잠금을 풀고 재료를 두 번 획득하는 경우를 시험해 문제를 찾아 달라」.

### 1. 완전 탐색은 무리인가 — 아니다

현실적인 판에서는 **이미 완전 탐색이 가능하다.** 제보의 32개 목표를 옛 탐색으로 상한 없이 돌리면 **1,077,405 노드 / 349ms**에 최적해를 증명하고 끝난다. 상한 20만은 그 18%에서 잘리고 있었다. 막힌 것은 문제의 크기가 아니라 **분기 방식**이었다.

**옛 방식**: 기프트마다 「(층, 팩) 칸」을 분기한다. 한 팩은 열 개 안팎의 층에 들어갈 수 있으므로 팩 수 × 층 수만큼 가지가 생긴다.

**새 방식**(`src/core/search.ts` 전면 교체):

- **팩만 분기한다.** 한 기프트를 주는 팩은 보통 한두 개다.
- **층은 이분 매칭이 정한다.** 고른 팩들을 서로 다른 층에 앉힐 수 있는지는 쿤 알고리즘으로 판정하고(팩 추가 = 증대 경로 하나, 되돌리기 = 그 경로만 역재생), 최종 층 배정은 **횡단 매트로이드 그리디**로 뽑는다 — 이른 층부터 훑어 매칭이 커지는 층만 남기면 층 합 최소가 보장된다.

결과(같은 판, 같은 답):

| | 노드 | 시간 | 완전 탐색? |
|---|---|---|---|
| 옛 탐색 (상한 20만) | 200,001 | 61ms | ✗ |
| 옛 탐색 (상한 해제) | 1,077,405 | 349ms | ✓ |
| **새 탐색** | **319** | **4ms** | **✓** |

품질 검증:

- 무작위 200개 시나리오 중 **양쪽 다 완전 탐색으로 끝난 197개에서 결과가 완전히 동일**(팩 수·놓침 수·층 합). 새 탐색이 다른 최적해를 고르지 않는다.
- 과대 입력 13개(전용 기프트 28~60개를 한꺼번에 고른 판, 새 탐색도 상한에 걸린다)에서 **9개는 새 탐색이 더 많이 확보, 4개는 동일, 나빠진 것 0개.**
- 상한은 20만 → **6만**으로 낮췄다. 새 노드가 옛 노드보다 비싸고(매칭), 걸리는 판에서는 상한을 두 배로 올려도 기프트 한 개를 더 건지는 정도라 최악 시간(≈180ms/회)을 택했다.

### 2. 「반드시」로 올리면 확보가 줄던 두 번째 원인

M22에서 정렬을 고쳤지만, 같은 판에서 **서릿발 발자국(9410)을 반드시로 올리면 31/32**가 되는 경우가 남아 있었다. 이번에는 근사 탐색의 사고가 아니다 — 두 계획 모두 **완전 탐색**이고, 목적 함수가 정확히 시키는 대로 동작한 결과였다.

9410을 반드시로 올리면 그 재료 얼어붙은 아우성도 반드시가 된다. 목적 함수의 최상위 항이 「반드시를 적게 버린 계획」이라, 플래너는 그 재료를 위해 1~5층 한 칸을 더 내주고 **헬스치킨(기프트 3개)을 통째로 버린다**. 정작 그 재료는 전부 보통일 때 **관측 슬롯 하나로 공짜로 건지고 있던 것**이었다.

고친 방법(`src/core/index.ts`의 `searchWithFallback`): 계획이 무언가를 버리게 되면 **우선순위를 전부 무시한 계획을 한 번 더 계산해서**, 그쪽이 더 많이 확보하고 밀려난 반드시들을 남은 관측 슬롯으로 덮을 수 있으면 그쪽을 쓴다. 관측으로도 못 덮는 진짜 충돌에서는 원래대로 반드시가 이긴다(1~5층으로 좁힌 회귀 케이스가 지킨다).

이제 제보 판의 다섯 경우(전부 보통 / 9235·9410·9761 각각 반드시 / 전부 반드시)가 **모두 32/32에 같은 층 배정**이다.

### 3. 얽힘 잠금 해제 — 그리고 재료 두 몫

M21에서 「재료가 겹치는 조합 둘」을 선택 불가로 막았다. 그 근거는 `entangle.ts` 머리말의 「재료를 두 번 주우면 둘 다 된다」였는데, **이 문장이 사실이 아니다**. 게임 규칙은 둘이다.

- **같은 E.G.O 기프트는 한 런에 하나만 가진다.** 보유 중이면 다시 제안되지 않는다(원본의 `mirror_unobservable_egogift_reason_is_owned` = 「보유 중」, `MirrorDungeonUI_5`의 「현재 보유 중인 E.G.O 기프트는 합성을 통해 얻을 수 있는 E.G.O 기프트에서 제외됩니다」).
- **조합은 재료를 소모한다.** 소모하면 그 재료는 다시 나올 수 있다.

그래서 잠금은 풀되(지시), **플래너가 몫을 세도록** 고쳤다. 잠금만 풀면 화면이 거짓말을 한다 — 아래가 지시대로 시험해서 찾은 문제다.

**시험 결과 (수정 전)**

| 목표 | 계획이 말한 것 | 실제 |
|---|---|---|
| 장관 + 부동 | 확보 2/2, **팩 1** (3층 육참골단에서 녹슨 칼자루를 **두 번** 획득) | 한 번만 나온다. 둘 중 하나만 가능 |
| 장관+부동+절경+탁마 | 확보 4/4, 팩 1 | 재료 4종 × 1개 → 최대 2개 |
| 회중시계 L·E·Y·P | 확보 4/4, 팩 1 (한 팩에서 8번 획득) | 재료 4종 × 1개 → 최대 2개 |

원인: `expandRequirements`는 요구사항을 `기프트:먹는조합`으로 키를 잡아 **두 줄을 만드는데**(`Requirement.count`도 있다), 그 뒤 모든 지도가 **기프트 id 하나**로만 되어 있었다 — `supplier`, `obtainedAtFloor`, 관측, 시작 기프트 전부. 그래서 두 줄이 같은 팩·같은 층을 가리키고, 조합 두 개가 다 된다고 나왔다.

**고친 것**

1. `requirementKey`(기프트 + 먹는 조합)를 `requirements.ts`에서 내보내고 `supplier`·`obtainedAtFloor`를 그 키로 바꿨다.
2. 탐색이 **한 기프트의 두 몫에 서로 다른 팩**을 준다(`packsTaken`). 이미 지나간 층이 주는 공짜 몫도 팩당 하나씩만 센다.
3. **관측은 한 몫만** 준다(`observe`가 요구사항 하나만 바꾸고, 구제·유연성 단계는 자기가 막힌 몫의 키를 넘긴다). 시작 기프트도 마찬가지.
4. 두 번째 몫을 줄 팩이 더 없으면 새 미해결 사유 **`ingredient-shared`**(「재료 겹침」)로 남긴다. `pack-conflict`로 두면 있지도 않은 층 충돌을 찾게 된다.
5. 두 몫을 다 확보했으면 새 경고 **`shared-ingredient`**로 **순서**를 알린다: 첫 번째를 들고 있는 동안에는 두 번째가 제안되지 않으니 **먼저 조합해 소모해야** 한다.

**수정 후**

| 목표 | 결과 |
|---|---|
| 장관 + 부동 (관측 끔) | 2/2 · 팩 2 — 3층 육참골단, 4층 육참골단 BokGak이 녹슨 칼자루를 한 몫씩 |
| 장관 + 부동 (관측 켬) | 2/2 · 팩 1 — 한 몫은 관측, 한 몫은 팩 + 순서 경고 |
| 절경 + 탁마 (관측 끔) | 1/2 — 낡은 칼자루는 복각 팩 하나에만 있어 두 번째 몫이 「재료 겹침」 |
| 회중시계 4종 | 4/4 · 팩 2 (시간살인시간 + 복각) |

데이터상 얽힌 조합 쌍은 **13쌍**이고, 공유 재료는 하나(해진 우산)만 범용, 나머지는 전부 전용이다. 그중 넷(깨진 안경·낡은 칼자루)은 공급 팩이 하나뿐이라 관측 없이는 둘 다 가질 수 없다.

## 읽는 순서

1. `src/core/search.ts` — 팩 분기와 `cheapestPlacement`(매트로이드 그리디), `augment`/`restore`의 되돌리기 로그, `packsTaken`.
2. `src/core/index.ts` — `searchWithFallback`(단조성), `requirementKey`로 바뀐 `supplier`·`obtainedAtFloor`, `observe`의 한 몫 규칙, `ingredient-shared`·`shared-ingredient`.
3. `src/core/requirements.ts` — `requirementKey`.
4. `src/app/lib/entangle.ts` — 머리말(왜 막지 않는가)과 `blockedGifts`에서 사라진 얽힘 가지.
5. 테스트: `planner.test.ts`의 「shared ingredients」 3케이스와 「priority」 보강, `gifts.test.ts`·`app.test.tsx`의 잠금 케이스 갱신.

## 핵심 규칙

- **같은 기프트는 한 런에 하나뿐이다.** 두 조합이 같은 재료를 먹으면 몫을 따로 확보해야 하고, 그 몫들은 서로 다른 팩에서 온다.
- **기프트 id로는 「어디서 얻는가」를 셀 수 없다.** 그 자리는 전부 `requirementKey`다.
- **우선순위를 올려서 확보 수가 줄면 그 계획은 쓰지 않는다.** 관측으로 덮을 수 있는 한.
- **아이템 화면이 막는 이유는 「포함」 하나뿐이다.** 얽힘은 알리기만 한다.

## 검증 로그

- `npm run check` 통과(325 tests, 신규 3 + 보강 1). `npm run build` 성공. `public/data` 변경 없음.
- 탐색 동치성: 무작위 200 시나리오 중 양쪽 완전 탐색 197개 전부 동일, 과대 입력 13개에서 9승 4무 0패.
- 단조성: 제보 판의 다섯 경우 전부 32/32, 층 배정·관측까지 동일. 「진짜 충돌에서는 반드시가 이긴다」 기존 케이스 유지.

- CLI/스크립트로 얽힌 13쌍의 공유 재료 공급 팩을 전수 확인.

## 남은 것

- **한 층 안의 순서는 검사하지 못한다.** 「먼저 조합하고 다시 줍기」가 그 층 노드 배치상 정말 가능한지는 알려 주지 않는다(경고로만 알린다).
- **런 중간의 「보유」는 한 몫으로 세지 않는다.** 이미 가진 재료가 두 조합에 걸리면 두 줄 모두 보유로 본다.
- `Requirement.count`(한 레시피가 같은 재료를 두 개 요구하는 경우)는 여전히 쓰이지 않는다. 현재 시즌 데이터에 그런 레시피는 0개다.
- 노드 상한은 여전히 고정(6만)이다.
