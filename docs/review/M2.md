# M2 — 루트 계산 코어

커밋: `M2: 루트 계산 코어와 시나리오 테스트`

## 무엇을 했나

덱과 원하는 기프트를 받아 층별 테마팩 루트를 계산하는 순수 TypeScript 모듈입니다. React·DOM·fetch를 쓰지 않고(ESLint가 막습니다), 같은 입력이면 같은 출력을 냅니다.

## 읽는 순서

**테스트부터 읽는 편을 권합니다.** 시나리오가 게임 상식과 맞는지가 코드보다 중요합니다.

1. `src/core/__tests__/planner.test.ts` — 시나리오 32개
2. `src/core/types.ts` — 입력·출력 모양
3. `src/core/index.ts` — `planRoute()`의 9단계 흐름
4. `src/core/requirements.ts` — 조합 전개와 레시피 선택
5. `src/core/search.ts` — 팩 배정 탐색
6. `src/core/deck.ts` — 덱 분석과 조건 판정
7. `src/core/starting.ts` — 시작 키워드 기프트

## 계산 흐름

1. **덱 분석** — 출격 6인 / 편성 12인 / 대기 인원별 키워드·소속 집계
2. **요구 확장** — 조합 기프트를 재료로 재귀 전개
3. **범용 분리** — 루트로 노릴 가치가 없는 기프트를 걸러냄
4. **시작 기프트** — 키워드 풀에서 원하는 것이 있으면 1개
5. **팩 배정** — 분기한정 DFS
6. **기프트 관측** — 루트로 못 덮은 것에만 별빛
7. **조합 일정** — 재료가 모이는 가장 이른 층 이후
8. **경고 생성** — 9종
9. **조립**

## 설계 판단 세 가지

**1. 탐색을 "층"이 아니라 "요구 기프트" 기준으로 한다.** 층 기준이면 분기 계수가 "층당 팩 수"(수십)이지만, 요구 기준이면 "기프트당 (층,팩) 조합 수"(대개 10 미만)입니다. 팩 하나가 여러 요구를 동시에 채우는 경우도 자연스럽게 처리됩니다. 15층·요구 20개에서 100ms 이내를 테스트로 고정했습니다.

**2. 범용 기프트는 루트로 노리지 않는다.** 전용이 아니고 팩의 20% 이상에 등장하는 기프트는 특정 팩을 강제해도 확정 획득이 아닙니다. 루트를 왜곡하는 대신 "범용 드랍 — 확정 아님, 상점과 새로고침을 쓰라"고 안내합니다. **이 기준(20%)이 적절한지 봐 주세요.** `data/curated/rules.json`의 `generalGiftPackShare`로 조절합니다.

**3. 상점 합성 칸에 맞는 레시피를 고른다.** 진혼(9088)에는 3재료 레시피(요리 비법 전서 포함)와 4재료 레시피가 있습니다. 후자는 일반 상점의 합성 칸 3개를 넘으므로, 게임이 안내하는 대로 하위 재료부터 조합하는 2단 체인을 선택합니다.

**4. 관측은 기본 지출이 아니라 대체 수단이다.** 처음에는 관측을 먼저 배정했더니 별빛 270을 쓰면서 쉽게 구할 기프트에 낭비했습니다. 지금은 탐색을 먼저 돌리고 **못 덮은 기프트에만** 씁니다.

## 테스트가 고정한 규칙

| 시나리오 | 기대 |
|---|---|
| 상납된 시가(교본 전용) | Hard 5층에 교본 배정 |
| 같은 기프트, Normal 계획 | `no-pack-in-range` + "Hard로 바꾸라" 경고 |
| 교본·검과 작품 전용 동시 요구 | `pack-conflict` (둘 다 Hard 5층에만 등장) |
| 같은 요구 + 관측 허용 | 관측 1개로 해결, 미확인 비용 경고 |
| 같은 요구 + 10층까지 계획 | 평행중첩 층으로 분산, 미해결 0 |
| 6층 이상 계획 | Hard 1층부터 강제 + 사유 경고 |
| 진혼 | 2단 조합 체인, 각 단계가 합성 칸 이내 |
| 교차 키워드(9083) | 참/관/타 3종 필수 + 덱 키워드 우선 2종 |
| 결정성 | 같은 입력 → 동일 JSON |
| 제약 | 팩 중복 없음, 층·모드 가용성 준수 |
| 회계 | 모든 요구가 계획 또는 미해결에 나타남 |
| 성능 | 15층·요구 20개 100ms 이내 |

## 봐 주셨으면 하는 점

1. **미해결 사유 문구가 이해되는지.** `no-pack-in-range` / `pack-conflict` / `hard-only` / `fusion-ingredient-unresolved`의 한국어 설명이 실제 상황을 정확히 말하는지.
2. **범용 임계값 20%**가 적절한지. 너무 낮으면 쓸데없이 팩을 강제하고, 너무 높으면 구하기 어려운 기프트를 방치합니다.
3. **관측 정책**이 맞는지. 지금은 "못 덮은 것만"인데, 사용자가 "확실히 챙기고 싶다"면 더 적극적으로 쓰는 옵션이 필요할 수 있습니다.
4. 팩 선택의 tiebreaker 순서: 미커버 최소 → 필요 팩 최소 → 이른 층 → 낮은 id. 별빛 최소화를 더 앞에 둘지.

## 알려진 한계

- 관측 비용이 실제로 어떻게 오르는지는 층별 순서에 따라 달라지는데, 지금은 "필요한 팩마다 1회씩, 순서대로 20/30/40…"으로 단순 계산합니다.
- 히든 팩(3001)은 관측으로 부를 수 없어 계산에 넣지 않습니다.
- 조합 성공 확률(재료 2·3·4개에 따라 0.6/0.9/0.99)은 데이터에 있지만 아직 UI에 노출하지 않습니다.
